# 最短验证路径运行指南

本指南是 Skill 运行行为的唯一权威。学习笔记用于人的理解，`COVERAGE.md` 只追溯来源，案例只帮助迁移；它们都不覆盖本指南。

## 核心语言

- **最短验证路径**：在完整投入前，以最低必要成本取得足以继续、修改或放弃创新点的关键证据。
- **生死问题**：一旦答案为否，就会使当前创新点失去继续投入理由的问题。
- **可验创新点卡**：把模糊 idea 转成可检验主张的交接物。
- **验证前沿**：当前所有阻塞已解除、最值得立刻执行的一项验证。
- **验证档案**：跨轮次保存假设、证据、路径、结果与决定的单一事实来源。

## V0｜先检查依赖和边界

每次运行先完成 SKILL.md 中的可选增强预检。增强 Skill 缺失时，不停止基础验证；应记录缺失项并跳过对应增强步骤。只有用户明确要求安装外部 Skill 时，才给出安装地址和命令 `npx skills@latest add mattpocock/skills`。项目尚未配置 issue tracker 与 domain docs 时，先说明限制，再使用当前对话和用户提供材料完成能完成的验证。

`AI Research/【验】` 一类材料只能支持“如何验”的方法论；具体创新点的科学主张、参数和阈值必须来自用户材料、原始数据、领域文献、官方文档或可检查代码。

## V1｜可验创新点卡

卡片必须包含：

1. 用户的创新点原话；
2. 研究对象与使用情境；
3. 当前基线及其痛点；
4. 拟议改变；
5. 预期作用机制或因果链；
6. 预期可观察结果；
7. 问题假设；
8. 方案假设；
9. 当前认为最致命的不确定性；
10. 可用数据、代码、设备、时间和人员；
11. 明确限制与未知项。

只追问会改变验证路径的缺失信息，一次一个问题。事实由 Agent 查找，决定由用户作出。卡片未经用户确认，不进入路径设计，不创建档案。

## V2｜领域建模交接门

以下任一条件出现时，询问用户是否调用 `$grill-with-docs`：

- 术语模糊、重载或与现有 `CONTEXT.md` 冲突；
- 研究边界、成功含义或核心机制仍需用户决定；
- 选择会影响后续多个验证或研究项目；
- 需要固定规范术语；
- 决定可能同时满足“难逆转、缺少上下文会令人困惑、存在真实权衡”。

用户同意时输出：

```text
请调用 $grill-with-docs，围绕以下验证项目继续讨论：

创新点：<原话>
当前歧义：<逐项列出>
必须解决的决定：<逐项列出>
相关验证档案：<路径或尚未创建>
完成后返回：规范术语、已定边界、必要 ADR、更新文件路径。
```

输出后停止。用户拒绝时记录“暂不进入领域建模”及其风险，再继续。

## V3｜判断是否存在 0→1

存在以下任一风险时需要独立的 0→1 验证：做不出、无法重复、原理可能错误、关键效果可能不存在、应用价值可能不足、现有资源无法实施、与论文整体缺乏关联。

当“1”天然存在、工作只是收集和解释必然发生的数据，或不存在合理失败可能时，可以直接进入 1→10。简单不等于无需验证；判断依据是是否存在会使研究夭折的不确定性。

## V4｜双假设审查

每次都审查：

- **问题假设**：声称的痛点是否真实、关键且值得解决？
- **方案假设**：核心思路在最简条件下是否可能产生预期价值？

已有直接且适用的证据时标记“由既有证据覆盖”；仍有致命不确定性时生成路径；不存在独立风险时写明理由。一次审查可以得到零、一或两条路径。

## V5｜锁定生死问题

把完整方案拆成依赖链，逐项问：删除这一项后，是否仍能判断创新点值得继续？优先验证最上游、最不确定、失败后会使最多下游工作失去意义的环节。

不要按实验时间顺序寻找第一步。完成条件是每个可能使研究夭折的假设都已由证据或路径覆盖。

## V6｜先生成压缩候选

至少考虑适用的候选：

- 删除锦上添花的表征、优化和 SOTA 对比；
- 用商业现成材料、公开数据、标准样品或成熟模块替代自制环节；
- 从真实设备降到已知真值仿真；
- 从三维、全尺度、全系统降到保留核心机制的一维或子系统；
- 从体内、临床或复杂环境降到体外、理想或受控环境；
- 复现最接近的论文、代码或实验，再替换创新部分；
- 用单变量 Lite A/B 测试隔离核心思路；
- 用最低限度但足以观察目标差异的测量。

每个候选都说明保留了哪个核心机制、删掉了什么、可能引入什么失真。

## V7｜最短判据

在满足以下三个约束后比较预期总代价：

- **判别性**：结果能区分关键假设成立与不成立；
- **可诊断性**：失败时能区分假设失败与执行失败；
- **机制相关性**：简化后仍保留创新点赖以成立的机制。

总代价可以比较日历时间、金钱耗材、设备场地、样本数据、平台搭建、外部依赖、不可逆投入以及错误 Go/No-Go 的代价。这是操作化扩展，不是原始材料明列的固定分类。

## V8｜最小必要证据

先列出执行当前生死问题所需的证据，不做泛化综述。可调用 `research` 查一手来源；受限数据库由 Agent 生成检索式，用户执行并回传。

每项方法、参数、阈值和判断依据标记：

- **来源支持**：来源直接给出；
- **跨来源推断**：多个来源共同支持；
- **建议起点**：领域常规或探索性选择，不冒充来源值；
- **仍待核实**：材料不足。

参数只有在原文、代码或可检查数据中明确出现时，才标为来源支持。当前证据足以执行最小验证时停止扩大检索。

## V9｜路径契约

每条最短验证路径必须包含：

1. 路径名称与对应生死问题；
2. 一句话核心假设；
3. 最小实验、仿真、复现或分析步骤；
4. 自变量、因变量、控制变量和关键混杂；
5. 对照或已知真值；
6. 可观察量与最低检出能力；
7. 测试有效性检查；
8. Go、Revise、No-Go、Inconclusive 预设判据；
9. 最简资源、预计等待与外部依赖；
10. 执行关键参数的证据状态；
11. 每种结果后的下一动作；
12. 为什么它比候选路径更短。

阈值必须在看结果前预设；经验阈值标为建议起点，并说明由谁最终确认。

## V10｜执行和回传

Agent 能安全执行的检索、代码、仿真和数据分析直接完成。需要用户执行时，只交付当前验证前沿：操作步骤、质量检查、必须保留的原始记录、回传格式和停止条件。

物理实验回传至少包含时间、版本或批次、原始数据位置、偏离方案之处、异常观察和重复信息。代码回传至少包含环境、依赖版本、命令、输入、日志、输出和随机种子。

## V11｜先验测试，再判假设

收到结果后依次执行：

1. 只整理事实和数值；
2. 检查缺失、离群、平行样、重复性、版本和协议偏离；
3. 检查正负对照、已知真值和测量灵敏度；
4. 对照预设判据；
5. 拆解因果链，标记支持、反对或无数据；
6. 再作四态判定。

四态定义：

- **Go**：测试有效，最低成功标准满足；
- **Revise**：获得有效信息，但创新点、边界或路径需要修改后重验；
- **No-Go**：测试有效且检出能力足够，证据明确反对生死假设；
- **Inconclusive**：测试有效性或证据不足，只能诊断和重做。

“没有得到预期结果”本身不是 No-Go。异常来自代码、协议或平台时调用 `diagnosing-bugs`，并把最小复现变成下一轮检查。

## V12｜验证档案与项目升级

卡片确认后，从 `assets/validation-dossier.md` 创建档案。优先服从目标项目的 tracker 约定；无更具体约定时使用 `.scratch/<idea-slug>/validation.md`。

以下任一情况出现时询问是否调用 `$wayfinder`：跨多个会话、存在阻塞等待、需要多人协作、多个验证可并行、当前只能看清验证前沿而无法精确描述后续问题。

用户同意时输出：

```text
请调用 $wayfinder，为以下验证项目建立共享地图：

Destination：<获得何种足以决策的证据>
Notes：使用 validate-research-idea 的 GUIDE；验证档案为 <路径>；每个 ticket 产生决定证据，不交付完整研究。
Decisions so far：<一行一项>
Frontier：<当前可执行问题>
Not yet specified：<仍在迷雾中的问题>
Out of scope：<1→10 优化与完整论文工作>
```

输出后停止。详细答案只放在子任务或证据文件中，档案只保存一行决定摘要与链接。

## V13｜退出 0→1

- Go：所有生死问题已覆盖，明确进入 1→10 的范围；
- Revise：更新卡片、假设和判据，回到对应规则；
- No-Go：保存有效证据、放弃理由和可迁移发现；
- Inconclusive：保留当前假设，进入诊断或补证据。

没有真实执行结果时，唯一允许的状态是“验证路径已准备”，不能写成“创新点已验证”。

## 每轮完成检查

每轮结束前确认：

- 当前状态明确；
- 本轮只推进一个验证前沿；
- 所有新增事实都有证据状态；
- 测试有效性与假设判定分开；
- 验证档案已更新；
- 下一动作能够由 Agent 或用户直接执行。
